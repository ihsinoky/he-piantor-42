# 成果公開の方式と整理計画への提言

> **位置づけ（2026-11-08 PO判断）**：本書は提案段階の議論記録である。確定方針は計画書（`docs/repo-cleanup-plan.md`）0節を正とする。確定方針の要点：公開用は独立した別リポジトリとし、その GitHub Releases で配布物を出す。常時同期はしない。本書の「A支持」は方向として採用されたが、詳細（更新単位、配布の仕組み）は確定方針と別計画に従う。

## 1. 見解：Aを推す。ただし、公開側を常時同期する開発リポジトリにしない

POの「厳選した入口から、必要な人だけ原資料へ進む」という方針に賛成する。推奨は **A：公開用の別リポジトリを、節目ごとの編集済み成果として作る**。現行リポジトリは開発・判断・証拠の正本として残す。公開側は「何ができたか」「何を学んだか」「何が未検証か」から読める構造にする。

ただし「ライト層が圧倒的に多い」はPOの読者仮説であり、本調査で人数を裏付けたわけではない。また、読みにくさは別リポジトリを作るだけでは解消しない。同じIssue別報告を移すだけなら、入口の名前が変わるだけである。Aを支持する根拠は人数の推定ではなく、現状の資料構造と、公開時に選別・説明すべき内容が明確に違うことにある。

計画の棚卸しは14,920ファイルを対象とし、最新成果物も途中入力・失敗試行・検査器と同じ資格証跡ディレクトリに入っている。たとえばWingは単板4種と製造用パネル2種、ケースは17mm正／16mm検証版、Matrixは製品Wingではなく比較評価基板である。ここを初見の読者にパスから推測させるのは負担が大きい。一方、この結び付きは開発の再現・監査には有用で、読み物のための移動で壊したくない。

率直に言えば、Aでも二重管理は増える。**公開側にも全ADR・Finding・ダッシュボード・最新CADの可変コピーを維持する案には反対する**。それを求めるなら、コスト最優先のPO方針にはBの「同一リポジトリ内に薄い公開入口を設ける」方が合う。Aを選ぶ条件は、更新頻度と複製範囲を絞り、公開版が参照する開発版を固定することである。

## 2. 最初に解いておく事実のずれ

[README](../README.md) と [公開監査報告](public-release-readiness.md) は、2026-10-02の公開承認・可視性変更を完了と記録している。したがって、今回を「現行リポジトリを初めて公開するか」の二択として扱うのは、既存記録と合わない。本書では **完成成果をどう編集して届けるか** の選択と解釈する。現在のGitHub可視性は今回照会していないため、公開済みという記述は既存記録の確認結果である。

この区別は実務に効く。Aの厳選は、公開済みの履歴やPRを隠す手段にはならない。現行リポジトリを非公開に戻しても既存の複製を回収できない。原資料への誘導を約束するなら、対象資料が実際に外部から読めるかを公開時に確認する必要がある。未公開にする範囲がある場合は、公開できる根拠の抜粋を公開側に収め、原資料は非公開と明記する。

また、10月の監査は当時のcommit `795479e`、65コミット・134 blob等を対象とした履歴的な結果である。11月の製造資料・見積・外部資産を含む現在の全資料について、安全・権利確認が済んだという意味ではない。

## 3. AとBの比較

| 観点 | A：別の公開用リポジトリ | B：現行を整理して公開の入口にする |
| --- | --- | --- |
| 読者体験 | rootから概要・知見・利用物へ進める。clone対象も絞れる。ただし編集しなければ効果はない | READMEや公開用文書だけでも入口は改善できる。cloneやファイル一覧では大量の履歴資料も目に入る |
| 履歴・生データ | 公開側の履歴は編集・配布の履歴。開発の経緯は固定リンクで別に読む。既公開資料の秘匿にはならない | 開発履歴と成果の追跡が一箇所。全資料・Git履歴・PR等の公開範囲を別途確認する必要がある |
| 保守コスト | 出典対応・権利表示・配布物の確認が追加される。節目の固定版なら抑えられる。常時同期は高くつく | リポジトリ間の対応管理は不要。入口と状態の更新は必要。物理再配置まで行うと依存調査が重い |
| 後戻り | 公開側の構造・文章を変えても原証跡は保てる。公開済み内容そのものの回収はできない | 案内の変更は戻しやすい。大規模移動は旧リンク・実行パス・manifestの修復を伴う |
| AIによる開発作業 | 開発は現行で継続できる。公開側だけ読むAIには、条件・失敗例・未検証範囲の脱落による誤用リスクがある | 全根拠に届くが旧版を現行と取り違えやすい。索引・状態訂正はどちらの方式でも必要 |

Bの最小構成は「公開入口＋成果物索引＋履歴索引」であり、全ファイルの移動を必須にしない。これはAに対する有力な低コスト案である。Aの追加コストを許容する理由は、開発の証拠構造を保存したまま、公開側の分類や配布単位を読者の目的に合わせて設計できる点に置く。

判断を確かめるには、初見の読者に「何を作ったか」「再利用できる知見は何か」「どの版を取得すべきか」を入口から探してもらう。入口文書だけで足りるならBへ縮小できる。閲覧数の想定だけでサイト構築や同期基盤へ投資しない。

## 4. Aで公開する内容と構造

### 4.1 原則と構造案

以下は未作成の公開用リポジトリ内の案であり、現行パスの移動指示ではない。最初はMarkdownと必要な図・固定配布物で始め、専用Webアプリは前提にしない。

```text
README.md                 目的、成果の図、到達点、未検証事項、読む順序
insights/                 厳選した知見と、その適用条件・反例・根拠
story/                    主要な分岐と採用理由を短く説明する開発の物語
artifacts/README.md       部品構成、版・ピッチ・左右・用途別の取得案内
releases/<公開版>/        その版のマニフェスト、配布物、検証の範囲と再現案内
LICENSE.md / LICENSES/    公開側の配置に合わせたライセンス対応
THIRD_PARTY.md            採用資産の出典、版、改変、必要な通知
```

入口は「知見を読む」「構造・判断を知る」「設計・製造データを使う」の三つへ分岐させる。Issue番号・EDA内部名称の理解を先に要求しない。ADRの全訳・全要約は作らず、重要な選択と却下理由だけを物語に埋め込み、D番号へ戻れるようにする。

知見は [計画5.2節](repo-cleanup-plan.md#52-遡及finding候補採番は取り込み後) のK03/K08/K09/K12を初期候補とする。独立検証、評価条件と保証要件の区別、via–pad監査、基板–ケース引継ぎは、再作業を避けたい読者に具体的な価値がある。ただしK番号は候補で、F番号でも確定知見でもない。P5で原典照合されたものから選ぶ。K01/K02/K04を紹介する場合も、当時の版・固定条件での観測をツール一般の能力評価に広げない。

D-031のADR／Finding／プロセス・skillへの昇格を継承し、公開側に第四の知見台帳を作らない。公開記事は原記録の編集物であり、F/D番号・出典commit・対象条件・公開版を持つ。F-001は2026-11-06の部品分類についての記録で、現在の在庫案内として使わない。

### 4.2 成果物を使う人には、概要とは別に一式を渡す

配布対象は、Main Rev.4、評価用Matrix Rev.3、Wing Rev.3、ケースのうち、その公開版でレビューを通ったものに限定する。完成時に版が進んでいれば改めて正本を確定する。今の4対象を将来の完成版と固定しない。

Wingの左右・16/17mm単板と製造パネル、ケースの入力CSVと出力形状、CADとBOM/CPLを区別する。未選択のピッチを推奨製品と扱わず、試験用firmwareを完成Vial対応版と表示しない。設計上の検査合格と、製造業者受入れ・実機合格・製造承認は別欄にする。たとえば [Wing報告](issue-200-wing-rev3-stage2.md) の4.9429Vはモデル値であって実測保証ではなく、[ケース最終README](../hardware/case/issue-198-final/README.md) の17mm正も量産ピッチ決定を意味しない。

公開版のマニフェストは、開発リポジトリの完全なcommit SHA、元パス、配布先パス、SHA-256、採択D番号、必要なライセンス、検証範囲と未了ゲートを結ぶ。人が取得するZIP・BOM・CPL・STEP/STLに加え、改変・再現に必要なソース、ライブラリ、凍結入力、生成・検査手順と環境条件を依存単位で含める。最終PCBだけを抜き出して完結した設計源と呼ばない。重い原証跡は原資料へ戻す。

公開用の分かりやすい配置へ組み直すなら、隔離環境で読込み・生成・検査の成立を確認する。現行rootに依存するスクリプトがあるため、ファイルをコピーしただけで再現可能とはしない。検査結果の転載だけで済む固定閲覧パッケージは、その範囲を明示する。原証跡のmanifestや実行時パスを改変して新配置で検証したことにはしない。

### 4.3 原資料への誘導と更新責任

公開記事の短い結論の後に適用条件・失敗例・限界を残し、「詳しい根拠」からF/Dと対応する検査結果へ進める。開発repoのrootや動くブランチへのリンクだけで済ませず、`blob/<完全SHA>/<path>` 相当の固定参照を使う。Issue/PRは議論の補足とし、結論の根拠は可能な限り固定された文書・データにも残す。非公開・リンク切れの原典だけに依存する主張は公開しない。

更新は **今は公開候補と出典対応を内部で蓄積し、完成時に最初のまとまった版を出す**。それ以前の公開は、独立して価値があり検証範囲を固定できる節目だけに絞り、POが選ぶ。毎PR同期はしない。完成待ちで知見の整理まで遅らせる必要はなく、P1/P5は進める。

開発側で事実を訂正し、公開側は次の版へ一方向に取り込む。公開側で新しい不具合を見つけたら、開発側へ戻して評価・判断してから訂正を配布する。開発版は追随するが公開版は固定された時点の成果なので、差があるだけで陳腐化とはしない。公開日・対象版・既知の問題・後継版への案内を常に表示する。危険な誤用、重大な誤記、権利・秘密情報の問題は次の節目を待たず訂正する。

PMOが出典対応と公開差分をまとめ、実装者が配布物を検証し、POが対象範囲と公開を承認する運用を提案する。これは今回の指示書の役割分担に沿う提案であり、[governance](governance.md) のPMO read-only規定とのずれは、運用を正式化する際の確認対象である。

## 5. ダッシュボードとの関係

[計画5.6節](repo-cleanup-plan.md#56-ダッシュボードtaskの用途変更--po決定2026-11-08) の用途変更は決定済みとして尊重する。ダッシュボードはマイルストーン計画に対する現在位置を示す開発用の大局ビューである。公開入口は成果・知見・利用先を示す。両者が重なるのは「どこまで確かめたか」「次に何が残るか」だけで、目的と更新周期は違う。

公開入口に開発ダッシュボードを丸ごと複製・埋込みすることは勧めない。公開版が古いのに現在の進捗が表示されると、その配布版まで後続検証を通ったように見える。公開側には公開版時点の到達点を短く固定表示し、現在進行形を知りたい人へだけ開発側ビューを案内する。内部用情報を含む場合はそのビューを直接公開しない。

データの正はdocs、ダッシュボードはread modelという関係を維持する。[task/README](../task/README.md) の詳細状態同期規約と、計画5.5節・P3表の「既存画面の最新状態を表示」は、5.6節の「詳細ステータスの複写はしない」と整合させる必要がある。P3ではPMOがマイルストーンを提案しPOが確認し、実画面で完了／進行中／次のゲートを確認する合格条件へ具体化する。公開方式を理由に、この決定を差し戻したり公開専用の進捗正本を増やしたりしない。

## 6. 公開前に確認する範囲

### 6.1 ライセンスと帰属

[LICENSE.md](../LICENSE.md) は混合ライセンスのパス対応表である。自作hardware/mechanical/manufacturingはCERN-OHL-P-2.0、docs・software等はMIT、第三者資産には例外がある。公開側で配置を変えた場合、元repoのパス表をそのまま貼っても対象が対応しない。元パスと公開パスの対応に基づき公開側の表を作り、出典・著作権表示・ライセンス本文を配布物にも同梱する。「公開repo全体MIT」のような一括表示は避ける。

[第三者台帳](../hardware/lib/THIRD_PARTY.md) で確認できる具体例は、marbastlib、Keebio、RP2040-minimalと派生回路、QMKのCantor／Piantor座標由来の例外である。特に `hardware/layout/layout_source.json` と生成CSV/SVGはGPL-2.0-onlyの例外として記録されている。名前を変えたり座標変換したりして、自作扱いにしない。

一方、その台帳は現行Wing Rev.3を含む全成果物の最新監査を完了した証明ではない。新Wingの系譜は、[Rev.2配置定義](../hardware/case/issue-194-layout/definition-17mm-right.proposal.json) がStage 1の座標CSVを参照し、[Rev.3生成器](../hardware/case/issue-200-stage1/generate.py) がRev.2資産を読む形で続く。Cantor等のどの版・座標・形状を取り込み、現行PCB・CSV・ケース・図へ何が伝播したかを公開対象単位で追う。旧layoutだけの例外だから新成果物は無関係、とも、新成果物すべてが同じライセンス、とも本書では断定しない。

また、[Main Phase A-2 README](../hardware/kicad/qualification/issue-196-main-rev4-phasea2/README.md) はUDB-C-Legacyのcommit `2ecdd7e0482ecbd3ffe9af04966ab3555f7fc33c` を入力としており、[同梱LICENSE](../hardware/kicad/qualification/issue-196-main-rev4-phasea2/inputs/udb/LICENSE) はMIT・ai03の表示を持つ。配布する入力や派生資料に応じて通知を残す。検討時に取り込んだルータ実装、ライブラリ、図、メーカー資料も、公開側へ収めるなら個別に対象化する。

ここでの提案は既存の権利記録に基づく確認作業であり、未監査の派生物の法的適合を認定するものではない。許諾根拠が未確認の資産はその配布版から保留し、必要な判断を得る。外部サイトの現行規約・最新版は今回調査していない。

### 6.2 秘密・個人情報・費用

「費用があるから非公開」と一律に扱うことには反対する。原価・見積条件は有益な知見になり得る。区分すべきなのは、公開可能な条件付きの価格・分析と、個別取引・本人情報・利用権限を露出する資料である。

| 対象 | 公開前の確認・扱い案 |
| --- | --- |
| 見積・費用 | 日付、枚数、基板版、実装方式、送料等の範囲を残す。担当者メール、見積番号、住所、取引条件、割引、顧客番号、支払情報、非公開合意の有無を確認する。旧価格を現行製造費と紹介しない |
| 個人・通信情報 | Git author/email、Issue/PR本文・添付・引用、サポート応答、スクリーンショットのアカウント名等を確認する。公開済みのGitHub名と新たな個人情報を区別する |
| 秘密情報・接続情報 | token、鍵、認証付きURL、セッションURL、ログ中の環境変数等を確認する。ZIP/gzや画像も対象に含める。今回の `.cleanup-runtime/` は配布しない |
| 外部・内部資料 | メーカー図、サポート回答、ツールソース、契約や内部運用情報について、再配布範囲と必要な匿名化・抜粋を確認する |

Aの公開側は選別したツリー・配布物・これから作る公開履歴を確認すればよいが、現行repoへのリンク先を公開可能と判断するには、そちらの履歴・PR・Actions・添付等の確認も必要になる。既存監査以降の追加分を特定できるなら差分を中心に進め、監査範囲を記録する。Aによって全履歴監査が不要になる、と説明しない。

公開用に伏せた派生資料は原本と区別し、編集内容・理由を管理する。秘密情報が既公開履歴に見つかった場合は、新repoへの移動や最新ツリーからの削除では解消しない。資格情報の失効等も含む別の対応として扱い、整理計画の通常PRで履歴を書き換えない。今回の文書調査は全ファイルの公開監査を実施したという報告ではない。

## 7. Bを選ぶ場合の最終整理と費用

Bでも、まずREADMEから概要・知見・最終成果物へ進める入口を作り、P3/P4で現行と履歴を区別する。公開のために14,920ファイルを改名・再配置する必要はない。深いパスは索引で吸収する。この構成なら、Aへの追加投資を避けられ、あとから公開入口を抽出する余地も残る。

構造自体を変えることまで求めるなら、P7でソース・ライブラリ・入力・検査器・権利表示をまとめた移動単位を調査し、P8で順次移動する。現行の検査器にはroot・相対パスへの依存があり、ケースにはWing確定CSVと凍結コピーがある。旧リンク案内、manifest対応、読込み・再現確認が費用の中心となる。見た目だけの整理のつもりで設計検証まで巻き込むリスクがある。

履歴は通常コミットで保持する。`git mv` は過去のGit blobやPRを消さず、容量や公開範囲を小さくする効果もない。通常のrevertは配置を戻せても外部の旧リンクを自動修復しない。履歴を消すことがBの成立条件になったら、現行計画の「履歴を壊さない」前提とは別の判断であり、本書は推奨しない。

## 8. 整理計画への具体的な変更提案

Aを採る場合も、開発者・AIが正本を選べなければ編集元が不安定になる。P3/P4を不要にする案には反対する。一方、公開で見栄えを整える目的の物理移動は、開発側で行う理由が弱くなる。

## 9. 読んだ根拠と本書の限界

作業規約・論点は `.cleanup-runtime/discussion-brief.md` 全文を基準とした。計画書の棚卸し・4節の配置案・5節の知見／ダッシュボード・6節のフェーズを照合し、README、公開監査報告、LICENSE、第三者台帳、project-status、task/README、governance、現行Wing／Main／ケースの関連記録・入力を確認した。D-031とF-001は計画が参照するPR #192のcommit `627fdcf83391a112a74f8a367b5e52a3bd0a8794` の本文をローカルGitから読んだ。mainへ取り込み済みとは扱っていない。
