## Workflow suitability and limiting mechanism

All attempted routing intent is represented in Python. Regeneration is
non-interactive, with no GUI action or GUI-authored hidden state. Ordinary diffs
expose endpoint selection, via coordinates, layer use and optional sketches;
computed copper needs capture/downstream DRC to review. The routing module is
approximately 140 lines, including both variants; 147 additional requests are
selected systematically, not hand-written segment by segment. One manual
escape adds two positions and three requests. Existing six routes/two vias are
inherited unchanged. Codex can create/review this intent and run the pipeline.

The limiting mechanism is **global layer/fanout/path planning**, not lack of a
Route constructor or route-all CLI. Single-layer endpoint trees leave 40 physical
connections missing. Specifying a second-layer span does not solve reaching that
layer from a crowded MCU pad. Expansion requires package escape placement,
layer allocation, route ordering/sketch changes and repeated physical verification
across many nets. No supported automatic source helper for those combined tasks
was established in the installed pins. Constraints, control points and via
structures describe local intent; they do not supply this planner.

This evidence does not prove that an expert cannot finish the board manually,
or that every alternative placement/route ordering fails. It establishes that
these compact supported approaches did not complete this fixture, and that a
credible complete AI/source-controlled workflow has not been demonstrated.
A routine maintenance claim would currently depend on unqualified substantial
manual routing strategy, likely aided by GUI inspection. Arbitrary placement
sweeps or enumerating many sketches to force green would not establish suitability.
No such brute force, private API, generated-KiCad edit, external router or EDA
round-trip is used. Further investment belongs in the C4C assessment.
